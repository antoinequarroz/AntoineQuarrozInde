# AQ-062 — Planifier et piloter les relances prospects

Validation humaine reçue le 14 septembre 2026 dans la conversation.

## Objectif

Faire de la prochaine relance une donnée explicite du prospect afin que le CRM remonte les dossiers dus ou en retard dans « Actions du jour », permette de préparer un e-mail Lumail avec confirmation humaine et donne une lecture simple de la charge commerciale sur mobile comme sur desktop.

## Critères d’acceptation

- Un prospect peut recevoir une date de prochaine relance et une note courte depuis les formulaires client et depuis une action rapide du CRM.
- Une relance planifiée apparaît le jour prévu puis reste visible comme « en retard » jusqu’à son traitement, son report ou son ignorance.
- En l’absence de date explicite, l’heuristique actuelle des prospects inactifs reste disponible afin de ne pas perdre les alertes existantes.
- Le CRM affiche les volumes « aujourd’hui », « en retard » et « planifiées » sans mélanger les organisations.
- Une relance prospect peut ouvrir une prévisualisation Lumail éditable et aucun e-mail ne part sans confirmation explicite.
- Après un envoi confirmé, la date du dernier contact est enregistrée, la relance courante est traitée et une prochaine date peut être programmée.
- Les actions existantes `Traité`, `Reporter`, `Ignorer` et `Annuler` continuent de fonctionner.
- Les contrôles ont une cible tactile d’au moins 44 px, un ordre de focus cohérent et des retours accessibles.

## Plan validable

- [ ] **Schéma CRM additif et tenant-safe** — ajouter à `public.clients` les colonnes `next_follow_up_at date`, `follow_up_note text` et `last_contacted_at timestamptz`, avec une contrainte de longueur sur la note et un index `(organization_id, next_follow_up_at)` limité aux prospects planifiés. Fichiers attendus : nouvelle migration Supabase créée par la CLI, baseline de production et tests de migration. Autorisé : colonnes nullable, index et commentaires ; interdit : modifier les lignes existantes, exposer une nouvelle table, affaiblir RLS ou accéder au `service_role` côté navigateur. Validation : migration locale, test de structure et vérification que les opérations serveur restent bornées par `organization_id`. Rollback : colonnes nullable ignorables par l’ancienne application ; aucune suppression automatique en production.
- [ ] **Contrat client et écritures auditées** — mapper les trois champs dans `Client`, le store et les réponses paginées ; valider les dates ISO et la note côté serveur ; journaliser les changements de relance sans inclure le corps complet de la note dans l’audit. Fichiers attendus : `app/types/index.ts`, `app/stores/clients.ts`, `server/api/clients.get.ts`, `server/api/clients.post.ts`, `server/api/clients.put.ts`, utilitaire de validation et tests ciblés. Autorisé : endpoints admin existants ; interdit : faire confiance aux champs d’organisation du client ou accepter une date/note non bornée. Validation : tests de normalisation et lectures/écritures scoped.
- [ ] **Planificateur commercial déterministe** — faire respecter la date explicite dans `buildCommercialTaskSuggestions`, distinguer aujourd’hui/retard et conserver l’heuristique d’inactivité comme fallback lorsqu’aucune date n’est définie. Ajouter un résumé des relances planifiées. Fichiers attendus : `app/utils/commercialTaskPlan.ts`, tests unitaires. Interdit : utiliser l’heure locale du navigateur pour le calcul métier ; la date Europe/Zurich fournie au planificateur reste la référence. Validation : cas futur, jour J, retard, fallback, report et restauration.
- [ ] **UX de planification mobile-first** — ajouter date et note au formulaire client, une action rapide de planification depuis les cartes CRM et des indicateurs « aujourd’hui / en retard / planifiées ». Les états chargement, succès, erreur et focus doivent être explicites. Fichiers attendus : `app/pages/admin/clients/index.vue`, `app/pages/admin/crm/index.vue`, éventuellement un petit composant admin réutilisable, tests statiques et E2E. Interdit : modal imbriquée, interaction uniquement au survol ou contrôle sous 44 px. Validation : viewport mobile et desktop, clavier, mode clair/sombre.
- [ ] **Prévisualisation Lumail pour les prospects** — étendre le plan de relance aux prospects dus, générer un brouillon sobre à partir du nom, de la date et de la note interne sans injecter cette note directement dans l’e-mail, puis réutiliser la confirmation anti-altération existante. Après succès, écrire `last_contacted_at`, traiter l’action commerciale et laisser proposer la prochaine relance. Fichiers attendus : `server/utils/pipelineReminderPlan.ts`, `server/utils/pipelineReminders.ts`, endpoints admin existants, CRM et tests. Autorisé : envoi manuel confirmé ; interdit : envoi automatique prospect, rappel d’un e-mail envoyé, contenu HTML non échappé ou destinataire non confirmé. Validation : prévisualisation, rejet d’un payload périmé, idempotence et audit.
- [ ] **Preuves de non-régression** — couvrir le parcours prospect → planification → action due → prévisualisation → envoi confirmé → historique, ainsi que le report et l’annulation. Fichiers attendus : tests unitaires, API/statiques et `e2e/admin.spec.ts`. Validation via Portly : tests ciblés, `npm test`, `npm run typecheck`, `npm run build`, budgets, tests de migrations et `git diff --check`.

## Statut d’implémentation

Les six étapes validées ci-dessus sont terminées. Les preuves locales couvrent la migration, les contrats serveur, la planification, l’UX mobile, Lumail, les compensations d’échec et les non-régressions.

## Sécurité, données et exploitation

- Les colonnes restent sur la table `clients` existante ; aucune nouvelle surface Data API n’est créée.
- Toutes les lectures et écritures applicatives passent par les endpoints admin authentifiés et ajoutent `organization_id = org.id` aux requêtes Supabase.
- La note de relance est une donnée interne : elle n’est jamais envoyée telle quelle à Lumail ni exposée au portail client.
- L’envoi prospect reste manuel et passe par la prévisualisation puis la confirmation existantes ; aucune ressource payante n’est déclenchée par la migration ou le chargement de page.
- Aucun secret, changement d’authentification, dépendance ou route publique n’est requis.
