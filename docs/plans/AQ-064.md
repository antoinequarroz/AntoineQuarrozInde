# AQ-064 — Conversion devis → facture transactionnelle

## Recherche source

Ce plan prolonge la cartographie de `docs/research/AQ-063.md` et les revues indépendantes du 14 septembre 2026. Le schéma actuel rend le numéro de facture unique par organisation, mais ne rend pas `quote_id` unique et la conversion est répartie sur plusieurs requêtes Supabase.

## Critères d’acceptation

- Deux conversions concurrentes du même devis retournent la même facture, avec exactement une création.
- Une facture liée à un devis contient toutes ses lignes ou n’existe pas ; aucun état partiel n’est observable.
- Le devis devient accepté dans la même transaction que la facture et ses lignes.
- Un devis brouillon, refusé ou appartenant à une autre organisation ne peut pas être converti.
- Une répétition confirmée retourne `created: false` sans nouvel audit ni nouvelles lignes.
- La migration est append-only, tenant-safe, testée localement et réversible par désactivation de la nouvelle route/RPC, sans suppression de données.

## Plan ordonné

- [x] **Écrire la migration de garantie d’unicité.** Objectif : ajouter un index unique partiel sur `(organization_id, quote_id)` lorsque `quote_id is not null`. Fichiers attendus : une nouvelle migration horodatée, le baseline de production et un test pgTAP dédié. Autorisé : index/contrainte append-only ; interdit : modifier une migration déjà appliquée, supprimer ou réécrire des factures. Tests : détection préalable de doublons, reset DB, lint, advisors et pgTAP. Validation : `npm run test:db`. Sécurité/rollback : vérifier les doublons avant création ; rollback applicatif en conservant l’index, car le retirer réouvrirait le risque de corruption.

- [x] **Créer une RPC de conversion atomique.** Objectif : verrouiller le devis tenant-scopé, vérifier son statut, retourner la facture existante ou créer facture et lignes puis accepter le devis dans une seule transaction. Fichiers attendus : même migration append-only et test pgTAP. Autorisé : fonction `security invoker`, `search_path` vide, exécution `service_role` uniquement ; interdit : accès `anon`/`authenticated`, service role côté navigateur ou confiance dans des totaux fournis par le client. Tests : autre tenant, brouillon, refusé, lignes invalides, collision et répétition. Validation : pgTAP prouve atomicité et permissions. Sécurité/rollback : aucune donnée partielle après exception ; ancienne implémentation conservable temporairement derrière la route serveur.

- [x] **Basculer la route serveur sur la RPC.** Objectif : remplacer le check-then-insert de `/api/quotes/convert` par l’appel transactionnel et conserver le contrat `{ created, invoice }`. Fichiers attendus : route de conversion et tests API ciblés. Autorisé : confirmation littérale existante et audit seulement lorsque `created: true` ; interdit : journaliser les montants, accepter un statut interdit ou exposer une erreur SQL brute. Tests : deux requêtes en `Promise.all`, répétition, refus, autre organisation et erreur transactionnelle. Validation : tests ciblés, typecheck et `git diff --check`. Sécurité/rollback : organisation issue de `requireAdmin` uniquement ; rollback vers l’ancienne route sans retirer la contrainte unique.

- [ ] **Exécuter la porte E2E AQ-063/AQ-064.** Objectif : exécuter le scénario sandbox authentifié déjà préparé, vérifier conversion concurrente, paiement via la modale, retour arrière et nettoyage exact. Fichiers attendus : `e2e/business-flow.spec.ts` seulement si une correction de stabilité est justifiée. Autorisé : organisation `AQ E2E Sandbox` et identifiants exacts ; interdit : production réelle, nettoyage par motif large ou secrets dans les logs. Tests : Playwright avec `E2E_ADMIN_*`, puis suite complète, build et test DB. Validation : zéro skip et zéro échec. Sécurité/rollback : supprimer uniquement les IDs créés par le test ; toute absence d’identifiant bloque le déploiement.
