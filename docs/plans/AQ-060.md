# AQ-060 — Livraison contrôlée des migrations Supabase

## Critères d'acceptation

- [ ] Une pull request continue à tester toutes les migrations localement sans secret, accès distant ni déploiement.
- [ ] Un push `main` attend une approbation humaine `Production` avant de pouvoir lire les secrets ou modifier Supabase/VPS.
- [ ] La livraison détecte l'historique distant et présente un dry-run avant toute mutation.
- [ ] Toute migration en attente déclenche d'abord un dump PostgreSQL métier chiffré; aucun fichier clair ni secret n'est téléversé.
- [ ] Seules les migrations versionnées absentes sont appliquées, puis une seconde vérification prouve l'alignement local/distant.
- [ ] Le conteneur n'est déployé qu'après une promotion réussie; un échec conserve l'application précédente et bloque les E2E.
- [ ] La procédure explique explicitement que le rollback SQL est manuel et exige des migrations rétrocompatibles.

## Plan ordonné

### 1. Modéliser un plan de promotion vérifiable

- **Objectif :** ajouter un utilitaire pur qui normalise le tableau rendu par `supabase migration list` 2.113.0 et distingue alignement, versions locales en attente et divergence distante.
- **Fichiers attendus :** `shared/utils/supabaseMigrationPlan.ts`, `tests/supabase-migration-plan.test.ts`.
- **Autorisé :** validation stricte des timestamps et listes triées; erreurs fermées sur sortie inconnue.
- **Interdit :** appel réseau, secret, correction automatique de l'historique ou supposition qu'une migration distante inconnue est sûre.
- **Validation :** fixtures alignées/en attente/divergentes/malformées avec Vitest.
- **Sécurité / rollback :** code pur supprimable sans effet distant.

### 2. Construire la promotion distante bornée

- **Objectif :** ajouter `scripts/ops/promote-supabase-migrations.sh` avec `HOME` temporaire, CLI épinglée, liaison explicite, liste et dry-run; si nécessaire, dump `public` schéma+données, chiffrement age, checksum, push puis seconde vérification.
- **Fichiers attendus :** script, éventuel helper Node ciblé, tests avec faux binaires et fixtures.
- **Autorisé :** `supabase link`, `migration list --linked`, `db push --linked --dry-run`, `db dump --linked`, `db push --linked --yes`, `age`, `sha256sum`.
- **Interdit :** `db reset`, `migration repair`, `--include-all`, seed/roles, logs debug, fichier SQL clair persistant, vraie connexion dans les tests.
- **Validation :** `bash -n`, ordre des appels, zéro migration sans dump/push, nettoyage sur succès/échec, aucun secret dans les sorties.
- **Sécurité / rollback :** l'échec stoppe avant le VPS; l'archive chiffrée est la preuve de reprise, pas un rollback automatique.

### 3. Ordonner la livraison GitHub

- **Objectif :** étendre le job `deploy` après `quality + database` pour installer la CLI/outillage, valider les quatre paramètres Production, exécuter la promotion, téléverser uniquement `.age`, `.sha256` et le manifeste, puis conserver le déploiement SSH et les contrôles AQ-058.
- **Fichiers attendus :** `.github/workflows/ci.yml`, `tests/release-pipeline.test.ts`, `tests/supabase-preflight.test.ts` ou test AQ-060 dédié.
- **Autorisé :** environnement `Production` unique, artefact à rétention bornée, conditions explicites sur push `main`.
- **Interdit :** secrets sur PR, `pull_request_target`, permissions en écriture inutiles, déploiement avant promotion, artefact SQL/tar non chiffré.
- **Validation :** tests statiques du graphe et des secrets, workflow PR vert, inspection de l'ordre réel.
- **Sécurité / rollback :** un échec de migration empêche SSH et E2E; l'image précédente reste active.

### 4. Documenter et configurer l'approbation humaine

- **Objectif :** mettre à jour l'exploitation puis configurer GitHub `Production` avec Antoine comme reviewer requis et `main` comme branche autorisée; ajouter les secrets sans jamais les lire ni les afficher.
- **Fichiers attendus :** `docs/operations.md`, `.env.example` seulement si une variable opérateur locale est réellement nécessaire.
- **Autorisé :** documentation des noms, rotation, procédure d'approbation, récupération/déchiffrement de l'artefact et révocation.
- **Interdit :** valeur réelle dans Git, clé privée age dans GitHub/VPS, auto-approbation par script.
- **Validation :** lecture de la configuration GitHub sans valeur de secret et capture du job `waiting` lors de la première livraison.
- **Sécurité / rollback :** retirer les nouveaux secrets et la règle reviewer revient au déploiement AQ-059 sans modifier la base.

### 5. Vérifier et livrer

- **Objectif :** exécuter tous les contrôles, faire une revue sécurité/diff, publier la PR, puis observer après fusion l'approbation, la promotion, le SHA/santé et les E2E.
- **Fichiers attendus :** uniquement les corrections strictement liées à AQ-060 et les cases/preuves de ce plan.
- **Autorisé :** première livraison sans migration en attente; promotion réelle seulement si le dry-run l'exige et après approbation explicite.
- **Interdit :** migration de démonstration, modification de données pour tester, contournement de l'environnement GitHub ou restauration production automatique.
- **Validation :** `npm test`, `npm run typecheck`, `npm run build`, `npm run quality:budgets`, `npm run test:db`, `git diff --check`, checks GitHub et endpoints publics.
- **Sécurité / rollback :** arrêter avant toute mutation si un secret, reviewer, dump chiffré ou dry-run manque; rollback applicatif AQ-058, reprise SQL manuelle seulement.
