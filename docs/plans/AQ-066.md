# AQ-066 — Observabilité du parcours commercial

## Critères d’acceptation

- [x] Les erreurs de création de prospect, conversion de devis et paiement portent un identifiant de corrélation opaque et traçable jusque dans le back-office.
- [x] La télémétrie n’accepte ni secret, ni e-mail, ni contenu libre, ni donnée bancaire.
- [x] `/admin/errors` expose un résumé de santé borné dans le temps et des alertes menant à une action pertinente.
- [x] Toute lecture et écriture reste filtrée par organisation et protégée par `requireAdmin` ou par le contexte serveur canonique.
- [x] Les tests couvrent succès, panne externe et reprise idempotente sans duplication métier.

## Plan ordonné

- [x] **1. Définir le contrat de corrélation et de sanitisation**
  - **Objectif :** créer un identifiant opaque par opération et un événement commercial fermé (`lead`, `quote`, `invoice`, `payment`; `success`, `failure`, `recovered`) ne contenant que des identifiants techniques et codes d’erreur approuvés.
  - **Fichiers attendus :** nouveau `server/utils/commercialObservability.ts`, tests ciblés `tests/commercial-observability.test.ts`.
  - **Autorisé :** UUID généré côté serveur, en-tête `X-Correlation-ID` borné/validé, liste blanche de champs, écriture best-effort dans `audit_logs` ou `application_errors`.
  - **Interdit :** payload arbitraire, e-mail, nom, texte du message/devis/facture, référence bancaire, token, clé ou stack dans les réponses admin synthétiques.
  - **Validation :** tests de génération, rejet/remplacement d’un identifiant invalide et absence de clés sensibles; `npm test -- commercial-observability`.
  - **Sécurité / rollback :** aucun nouveau droit direct ni secret; retirer l’utilitaire laisse les tables existantes intactes.

- [x] **2. Instrumenter les trois ruptures critiques**
  - **Objectif :** propager la corrélation sur la création du prospect, la conversion atomique devis → facture et l’enregistrement du paiement, avec distinction création, panne et reprise idempotente.
  - **Fichiers attendus :** `server/api/contact.post.ts`, `server/api/quotes/convert.post.ts`, `server/api/invoices/payments.post.ts`, `server/utils/recordInvoicePayment.ts`, tests API existants et ciblés.
  - **Autorisé :** événements best-effort après résultat métier, codes de panne fermés, en-tête de réponse traçable, conservation des messages publics actuels.
  - **Interdit :** modifier les règles métier, contourner les RPC atomiques, dupliquer un audit, rendre un succès dépendant du monitoring ou exposer une erreur fournisseur/SQL.
  - **Validation :** succès corrélé, panne externe/DB sans fuite et retry `{ created: false }` corrélé sans deuxième facture/paiement; `npm test -- quote-conversion-api commercial-observability invoice-payments`.
  - **Sécurité / rollback :** le filtrage par `organization_id` reste obligatoire; retirer les appels d’instrumentation restaure le comportement précédent sans donnée métier à migrer.

- [x] **3. Fournir une santé commerciale privée et actionnable**
  - **Objectif :** agréger sur une fenêtre bornée les événements réussis, échoués et repris, identifier la dernière rupture par étape et produire une action interne sûre.
  - **Fichiers attendus :** nouveau `server/api/admin/commercial-health.get.ts`, extension de `server/api/admin/alerts.get.ts`, tests `tests/admin-commercial-health.test.ts`.
  - **Autorisé :** lectures agrégées de `audit_logs` et `application_errors`, fenêtre maximale bornée, compteurs et liens internes fermés.
  - **Interdit :** retourner message, stack, payload complet, incidents d’une autre organisation ou données globales à un non-propriétaire.
  - **Validation :** tests tenant A/B, fenêtre, état sain/dégradé et erreur de source; `npm test -- admin-commercial-health`.
  - **Sécurité / rollback :** endpoint protégé par `requireAdmin`; suppression de l’endpoint et de l’alerte suffit au rollback.

- [x] **4. Intégrer le résumé au back-office**
  - **Objectif :** afficher dans `/admin/errors` une synthèse lisible des étapes, l’identifiant copiable du dernier incident et une seule prochaine action par rupture.
  - **Fichiers attendus :** `app/pages/admin/errors/index.vue`, éventuellement un petit composant sous `app/components/admin/`, test UI ciblé.
  - **Autorisé :** états chargement/vide/erreur, responsive mobile, liens vers CRM/devis/factures/paiements, annonce `aria-live`.
  - **Interdit :** afficher des données sensibles, masquer les incidents existants, ajouter un graphe lourd ou déclencher une mutation depuis le résumé.
  - **Validation :** clavier, mobile, thème clair/sombre, état dégradé et copie de corrélation; `npm test -- admin-commercial-health`.
  - **Sécurité / rollback :** surface en lecture seule; retirer le bloc conserve l’écran d’erreurs actuel.

- [x] **5. Fermer les preuves de livraison**
  - **Objectif :** démontrer les cinq critères sans affaiblir les garde-fous existants.
  - **Fichiers attendus :** tests ciblés ci-dessus, mise à jour de ce plan et commentaire de preuve dans `ANT-16`.
  - **Validation :** `npm test`, `npm run typecheck`, `npm run build`, `npm run quality:budgets`; tous exécutés via Portly.
  - **Interdit :** déployer ou fusionner tant que revue et CI ne sont pas vertes.
  - **Rollback :** appels d’instrumentation et endpoint/UI sont retirables indépendamment; aucune migration destructive n’est prévue.
