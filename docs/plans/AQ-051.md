# AQ-051 — Plan d'implémentation du rapprochement bancaire

## Critères d'acceptation

- [x] Antoine peut importer un CSV bancaire de taille raisonnable depuis `/admin/payments` sans que le relevé complet soit envoyé au serveur.
- [x] Les lignes entrantes valides sont normalisées et les lignes rejetées sont comptées avec une explication.
- [x] Chaque ligne reçoit une correspondance exacte, probable, ambiguë ou absente selon référence, numéro de facture, montant, devise et solde.
- [x] Antoine peut corriger ou ignorer une proposition et doit confirmer explicitement avant toute écriture.
- [x] Une confirmation crée le paiement par le flux comptable canonique, met à jour le cockpit et reste auditée.
- [x] Le même mouvement bancaire ne peut pas être rapproché deux fois dans une organisation.
- [x] Les états chargement, erreur, vide, doublon, confirmation et succès sont accessibles, responsive et sans fuite d'erreur serveur.

## Tâches ordonnées

### 1. Ajouter l'identité anti-doublon des imports

- [x] **Objectif :** ajouter `bank_import_fingerprint` nullable à `invoice_payments`, avec index unique partiel par organisation et commentaire de schéma.
- **Fichiers attendus :** nouvelle migration append-only dans `supabase/migrations/`.
- **Autorisé :** ajout nullable, index unique partiel, commentaire ; aucune réécriture des paiements existants.
- **Interdit :** suppression ou mutation d'historique, changement des politiques/grants existants, restauration de production.
- **Tests :** test statique de migration confirmant colonne, unicité organisationnelle et absence de suppression.
- **Validation :** `npm test -- bank-reconciliation`.
- **Sécurité / rollback :** la colonne est sans effet pour les paiements existants ; rollback applicatif possible en laissant la colonne inutilisée. La migration n'est jamais supprimée après application.

### 2. Construire le parseur et le moteur de correspondance

- [x] **Objectif :** créer des fonctions pures pour détecter le séparateur, reconnaître les colonnes, normaliser dates/montants/références, rejeter les débits, produire une empreinte stable et scorer les factures ouvertes.
- **Fichiers attendus :** `shared/utils/bankReconciliation.ts`, `tests/bank-reconciliation.test.ts`, petit fixture CSV sous `tests/fixtures/` si nécessaire.
- **Autorisé :** CSV UTF-8, séparateurs `;`, `,`, tabulation, alias FR/EN documentés ; aucun paquet supplémentaire.
- **Interdit :** XML CAMT.053, PDF/OCR, exécution de formules, heuristique qui confirme un paiement.
- **Tests :** références SCOR/QRR normalisées, numéro de facture, montant unique, ambiguïté, décimales suisses, débit ignoré, champs manquants, empreinte stable.
- **Validation :** `npm test -- bank-reconciliation`.
- **Sécurité / rollback :** limite de fichier contrôlée dans l'UI ; les fonctions traitent le texte comme donnée opaque.

### 3. Exposer les candidats et confirmer une ligne côté serveur

- [x] **Objectif :** fournir une lecture manager des factures rapprochables et une confirmation transactionnelle qui recalcule empreinte/solde, insère le paiement bancaire, met à jour le statut, audite et conserve l'envoi de reçu existant.
- **Fichiers attendus :** `server/api/admin/payment-reconciliation.get.ts`, `server/api/admin/payment-reconciliation.post.ts`, extraction ciblée éventuelle dans `server/utils/invoicePayments.ts`, tests d'autorisation/organisation/idempotence.
- **Autorisé :** factoriser le cœur existant de `server/api/invoices/payments.post.ts` afin que manuel et rapprochement partagent exactement validation, verrouillage, audit et reçu.
- **Interdit :** route publique, accès client, confiance dans un solde/une empreinte fourni par le navigateur, insertion sans `organization_id`.
- **Tests :** `requireAdmin`, filtres organisation sur chaque requête, 400 données invalides, 404 facture, 409 doublon/surpaiement, succès et audit sans données excessives.
- **Validation :** `npm test -- bank-reconciliation invoice-payments payment-operations`.
- **Sécurité / rollback :** aucune écriture avant confirmation ; l'unicité DB protège les requêtes concurrentes ; les paiements restent annulables par le flux existant.

### 4. Ajouter le workflow de rapprochement au cockpit

- [x] **Objectif :** ajouter une action « Rapprocher un relevé », un import accessible, un résumé reconnu/rejeté, une liste de propositions avec niveau de confiance, sélection manuelle et confirmation individuelle protégée contre le double clic.
- **Fichiers attendus :** `app/pages/admin/payments/index.vue`, éventuel composant local sous `app/components/admin/` si la page devient trop dense, mise à jour de la brief de surface après revue.
- **Autorisé :** prolonger le monde existant violet/cyan et la hiérarchie exceptions-first ; conserver clair/sombre et cartes mobiles.
- **Interdit :** redesign global, auto-confirmation, affichage du contenu brut complet, écriture en masse sans revue.
- **Tests :** états sans fichier, fichier invalide, propositions exactes/ambiguës, sélection manuelle, confirmation, doublon, rafraîchissement du journal, clavier et mobile.
