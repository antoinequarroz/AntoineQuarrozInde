# AQ-068 — E2E mobile du back-office commercial

## Critères d’acceptation

- Tests sur un viewport mobile réaliste pour connexion et MFA.
- Parcours clients, devis, factures et paiements testés au toucher et au clavier.
- États chargement, vide, erreur et succès vérifiés sans débordement horizontal.
- Navigation, dialogues et formulaires restent accessibles et utilisables.
- La suite CI ne contient aucun test ignoré et produit des artefacts en cas d’échec.

## Plan ordonné

- [x] **Créer l’oracle mobile et l’authentification obligatoire.** Objectif : déclarer un projet Playwright mobile réaliste (profil de téléphone, tactile, viewport et user-agent cohérents), couvrir connexion, redirection protégée, challenge MFA et erreur, puis fournir des assertions partagées de viewport/focus. Fichiers attendus : `playwright.config.ts`, `e2e/helpers/admin-auth.ts`, un helper mobile ciblé et des tests d’authentification. Autorisé : configuration Playwright et données d’authentification injectées par environnement ; interdit : secret TOTP dans une capture, un log ou le navigateur au-delà du code à six chiffres généré. Tests : login avec MFA, mauvais code simulé, redirect sûr, cibles tactiles et clavier. Validation : suite ciblée locale via Portly avec zéro skip. Sécurité/rollback : aucune persistance nouvelle ; retrait du projet mobile restaure la configuration précédente.

- [x] **Prouver le parcours commercial mobile complet.** Objectif : exécuter client → devis → facture → paiement → CRM dans `AQ E2E Sandbox` sur le projet mobile, en utilisant les formulaires et prochaines actions visibles pour les étapes que le ticket doit garantir. Fichiers attendus : `e2e/business-flow.spec.ts` et helpers sandbox strictement nécessaires. Autorisé : données uniques et préfixées, en-tête d’organisation issu de la session, préparation API minimale lorsque l’UI ne fait pas partie du critère ; interdit : client réel, service role navigateur, nettoyage par motif ou duplication des paiements. Tests : toucher sur les actions principales, parcours clavier sur chaque dialogue, confirmation de conversion/paiement, retour CRM, idempotence et absence d’overflow à chaque étape. Validation : scénario mobile complet vert puis contrôle API final. Sécurité/rollback : IDs collectés dès chaque création et supprimés individuellement dans `finally`; tout ID incertain bloque le nettoyage.

- [x] **Couvrir la matrice chargement, vide, erreur et succès.** Objectif : rendre déterministes les quatre états de clients, devis, factures et paiements avec interception réseau, sans écrire de donnée métier. Fichiers attendus : nouveaux tests E2E mobiles focalisés et, seulement si une lacune produit est révélée, la page admin concernée. Autorisé : fixtures minimales non sensibles et réponses simulées ; interdit : masquer une erreur, reproduire des données de production ou modifier les contrats serveur. Tests : état annoncé aux technologies d’assistance, action de reprise, aucune donnée serveur brute, aucun débordement horizontal ni dialogue hors viewport. Validation : matrice 4 × 4 verte sur le projet mobile. Sécurité/rollback : fixtures locales supprimables sans impact applicatif.

- [x] **Durcir interactions tactiles et clavier.** Objectif : vérifier navigation mobile, ordre de tabulation utile, focus initial et restauré, fermeture `Escape`, scroll interne des formulaires, taille des cibles et soumission unique. Fichiers attendus : helper d’assertions mobile, `e2e/admin.spec.ts` et tests commerciaux ciblés. Autorisé : assertions DOM/accessibilité et petites corrections UI prouvées par un test rouge ; interdit : refonte visuelle générale du back-office ou changement de règles métier. Tests : interaction tactile Playwright, parcours clavier sans souris, axe WCAG A/AA sur les vues clés, zéro erreur/hydration warning. Validation : tests mobile et accessibilité verts. Sécurité/rollback : aucune donnée supplémentaire ; corrections UI isolées et réversibles.

- [x] **Fermer la porte CI et conserver les preuves d’échec.** Objectif : rendre obligatoires e-mail, mot de passe et TOTP pour la porte admin, échouer si un test est ignoré, et conserver rapport, trace, capture et vidéo en cas d’échec. Fichiers attendus : `.github/workflows/ci.yml`, `playwright.config.ts`, éventuellement un reporter Playwright minimal et son test unitaire. Autorisé : reporter machine local et artefacts sans secrets ; interdit : imprimer les variables, rendre les secrets optionnels en CI ou déployer quand la porte mobile échoue. Tests : preuve locale qu’un skip provoque un exit non nul, preuve qu’un échec crée les artefacts, YAML valide et suite E2E complète. Validation : quality → build → déploiement candidat → health/version → E2E desktop + mobile, zéro skip. Sécurité/rollback : rétention courte existante, artefacts limités aux dossiers Playwright et retour possible au reporter précédent sans toucher aux données.

## Validation humaine

Plan validé explicitement par Antoine le 15 septembre 2026.

## État de validation

- Profil `mobile-admin` basé sur iPhone 13, tactile et exécuté avec Chromium comme la CI.
- 8/8 scénarios mobiles passent localement, dont le login MFA réel, le refus sûr d’un code invalide et le parcours sandbox client → devis → facture → paiement → CRM.
- 40/40 scénarios Playwright desktop et mobile passent en série, sans test ignoré, en 2 min 14 s après la sécurisation des artefacts.
- 658/658 tests Vitest passent avec le runtime Python des Command Line Tools.
- Typecheck et build Nuxt passent ; `git diff --check` ne signale aucune erreur.
- Le reporter CI échoue explicitement lorsqu’un test est ignoré et écrit `test-results/safe-failure-report.json` avec uniquement le titre, le statut, la tentative et la durée.
- Les specs authentifiées désactivent explicitement traces, captures et vidéos afin qu’aucun mot de passe, code TOTP ou jeton de session ne soit téléversé ; les scénarios publics conservent les artefacts Playwright complets.
- Une exécution négative contrôlée sans identifiants a échoué comme prévu et n’a produit aucun `trace.zip`, PNG ou WebM, uniquement le rapport expurgé.
- La porte accessibilité de pull request cible explicitement le scénario `@credential-free`; sa reproduction CI passe 1/1 sans identifiants et sans test ignoré, tandis que l’audit admin complet reste dans la porte E2E post-déploiement authentifiée.
