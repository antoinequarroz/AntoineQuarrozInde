# AQ-058 — Pipeline de livraison ordonné et vérifiable

## Critères d'acceptation

- [ ] Une pull request exécute qualité et accessibilité sans toucher au VPS.
- [ ] Un push `main` déploie seulement après un job qualité réussi.
- [ ] Le déploiement utilise une clé SSH dédiée, un `known_hosts` vérifié et aucun secret versionné.
- [ ] Le job confirme que `/api/version` sert exactement le SHA fusionné et que `/api/health` est `ok` avant les E2E.
- [ ] Les E2E de production ne peuvent plus démarrer contre l'ancienne version après un push `main`.
- [ ] Un échec de build, de santé ou de version conserve le rollback existant et bloque les E2E.
- [ ] Les exécutions planifiées vérifient la production courante sans la redéployer.

## Plan

- [x] **Orchestration GitHub** — restructurer `.github/workflows/ci.yml` avec un job `deploy` après `quality`, environnement `Production`, conditions distinctes PR/push/schedule et `e2e` ordonné. Autorisé : jobs/conditions/permissions minimales; interdit : secrets en clair, déploiement de PR, migration Supabase automatique. Validation : tests statiques et lecture du graphe Actions.
- [x] **Déploiement SSH borné** — ajouter `scripts/ops/deploy-from-ci.sh` pour accepter uniquement un SHA Git complet, faire `fetch`/`checkout main`/`pull --ff-only`, vérifier que HEAD égale le SHA demandé puis appeler `deploy-release.sh`. Interdit : `reset --hard`, branche arbitraire, affichage de secrets. Validation : `bash -n` et tests des entrées invalides.
- [x] **Preuve post-release** — ajouter `scripts/ops/verify-production-release.sh` qui attend de manière bornée `/api/version` et `/api/health`, vérifie le SHA exact avec `jq` et échoue explicitement en cas de timeout. Validation : fixture HTTP locale succès/erreur et test statique du workflow.
- [x] **Tests et documentation** — ajouter `tests/release-pipeline.test.ts`, mettre à jour `docs/operations.md` avec l'ordre réel, les cinq secrets Production et la procédure de révocation/rollback. Validation : `npm test`, `npm run typecheck`, `npm run build`, budgets et `git diff --check`.
- [ ] **Installation contrôlée** — après revue, créer une clé Ed25519 dédiée, ajouter sa clé publique au VPS, enregistrer `VPS_SSH_PRIVATE_KEY`, `VPS_KNOWN_HOSTS`, `VPS_HOST`, `VPS_USER` et `VPS_PROJECT_DIR` dans l'environnement GitHub `Production`, puis exécuter une livraison réelle. Rollback : révoquer la clé dans `authorized_keys`, désactiver les secrets et revenir au déploiement manuel `scripts/deploy-vps.ps1`.
