# AQ-058 — Pipeline de livraison ordonné et vérifiable

## Besoin observé

Lors de la livraison du merge `6ecf08d`, le workflow GitHub `Quality` a lancé les E2E de production avant que le VPS ait terminé son déploiement. Les tests ont alors rencontré l'ancienne version (contrastes, route `/admin/accounting` et bouton de rapprochement absents), puis le rerun exécuté après stabilisation a réussi. Le prochain ticket doit supprimer cette fenêtre de course sans affaiblir les contrôles.

## Flux actuel vérifié

- `.github/workflows/ci.yml` exécute `quality` et `e2e` en parallèle sur tout push `main`; `e2e` ne dépend ni d'un déploiement ni d'une version attendue.
- `scripts/deploy-vps.ps1` se connecte manuellement au VPS, fait un `git pull --ff-only origin main`, puis délègue à `scripts/ops/deploy-release.sh`.
- `scripts/ops/deploy-release.sh` conserve l'image précédente, construit `candidate`, attend l'état Docker `healthy` et restaure `previous` en cas d'échec.
- `Dockerfile` injecte `APP_VERSION` et `APP_BUILD_TIME`; `server/utils/version.ts` les expose via `server/api/version.get.ts` sans cache.
- `server/api/health.get.ts` vérifie Nuxt et Supabase, et le healthcheck Docker de `docker-compose.yml` utilise cette route.
- `docs/operations.md` documente déjà la mise en ligne, le rollback, `/api/version`, `/api/health` et les E2E.

Le mécanisme de release côté VPS est donc déjà sûr. Le défaut se situe dans l'orchestration GitHub, qui ne connaît ni la fin du déploiement ni le SHA réellement servi.

## Intégrations et conventions

- Le workflow utilise Node `22.19.0`, `npm ci --legacy-peer-deps`, Vitest, `nuxi typecheck`, le build Nuxt, les budgets puis Playwright.
- Les secrets existants sont seulement `E2E_ADMIN_EMAIL` et `E2E_ADMIN_PASSWORD`; aucun secret SSH VPS n'est actuellement configuré.
- Un environnement GitHub `Production` existe, sans règle d'approbation obligatoire.
- Le dépôt distant du VPS reste sur `main` et accepte les mises à jour fast-forward; il ne faut pas introduire de `git reset --hard`.

## Architecture proposée

Sur un push `main`, conserver `quality`, puis exécuter un job `deploy` ciblant l'environnement `Production`. Ce job utilise une clé SSH dédiée stockée dans GitHub Secrets, vérifie strictement la clé d'hôte, met le VPS à jour par fast-forward et lance le script de release existant. Il attend ensuite que `/api/version` corresponde exactement à `github.sha` et que `/api/health` soit `ok`. Les E2E de production ne démarrent qu'après ce succès.

Les pull requests restent non déployantes : qualité et accessibilité uniquement. Les exécutions planifiées continuent de tester la production courante sans redéploiement. Un `workflow_dispatch` doit permettre une vérification manuelle, sans contourner les contrôles de qualité.

## Sécurité

- Ne jamais versionner une clé privée, un hôte SSH ou un contenu de `.env`.
- Utiliser une clé SSH dédiée à GitHub Actions, distincte de la clé personnelle, avec permissions minimales et révocation simple.
- Stocker la clé privée, l'hôte, l'utilisateur, le chemin projet et `known_hosts` dans les secrets de l'environnement `Production`.
- Refuser une clé d'hôte inconnue; ne pas utiliser `StrictHostKeyChecking=no` ni `ssh-keyscan` aveugle dans le workflow.
- Ne pas exposer les secrets dans les logs ou les artefacts.
- Vérifier le SHA distant avant la construction et le SHA public après le déploiement.
- Conserver le rollback Docker existant et ne pas modifier la base de données dans ce ticket.

## Tests et preuves attendues

- Test statique du graphe de jobs : `deploy` dépend de `quality`, et `e2e` dépend du résultat du déploiement sur push `main`.
- Test statique de la sécurité SSH : secret de clé, `known_hosts`, absence de désactivation du contrôle d'hôte et absence de clé en clair.
- Test du script de vérification de production : succès sur SHA/health correspondants, timeout borné sinon.
- `bash -n scripts/ops/*.sh`, `npm test`, `npm run typecheck`, `npm run build` et `npm run quality:budgets`.
- Essai réel : PR sans déploiement, puis merge testant l'ordre `quality → deploy → e2e` et la version publique.

## Risques et questions à valider

- L'automatisation nécessite de créer une clé SSH dédiée et cinq secrets GitHub Production. C'est une modification de sécurité externe qui doit être validée avant installation.
- Le workflow ne doit pas appliquer automatiquement les migrations Supabase : une migration incompatible doit rester une étape explicitement contrôlée jusqu'à la mise en place d'une vraie préproduction de base.
- Vercel n'est pas la cible de production; son preview historique ne doit pas piloter la livraison VPS.
