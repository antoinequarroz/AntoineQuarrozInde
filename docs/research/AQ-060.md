# AQ-060 — Recherche : livraison contrôlée des migrations Supabase

## Résultat attendu

Promouvoir les migrations Supabase versionnées avant le conteneur applicatif, après une approbation humaine unique et une sauvegarde chiffrée, sans exposer de secret ni prétendre qu'un rollback SQL automatique est sûr. Une migration ou une vérification distante en échec doit laisser l'ancienne application active et bloquer la suite de la livraison.

## Preuves du dépôt

- `.github/workflows/ci.yml` exécute `quality` et `database`, puis lance directement `deploy` sur chaque push `main`. Le job `database` ne connaît aucune production : il reconstruit une pile locale avec `npm run test:db`. Le job `deploy` ne reçoit que les cinq secrets SSH du VPS.
- `scripts/ops/test-supabase-migrations.sh` isole `HOME`, interdit toute liaison distante et rejoue `supabase/schema.sql`, les 18 migrations de `supabase/migrations/` et pgTAP. AQ-060 doit conserver ce préflight de PR tel quel.
- `scripts/ops/deploy-from-ci.sh` vérifie le SHA exact, avance `main` en fast-forward, puis délègue à `scripts/ops/deploy-release.sh`. Ce dernier conserve l'image Docker précédente et la restaure si le candidat n'est pas sain, mais il ne traite pas la base.
- `scripts/ops/verify-production-release.sh` exige le SHA attendu et un `/api/health` dont l'application et la base sont `ok`. Il fournit déjà la vérification post-déploiement nécessaire après promotion du schéma.
- `scripts/ops/backup-supabase.sh` sauvegarde les données métier, l'inventaire Auth non secret et les médias depuis le VPS, avec copie Supabase et option R2 chiffrée. Cette sauvegarde quotidienne n'est toutefois ni transactionnelle ni garantie immédiatement avant une migration.
- `tests/release-pipeline.test.ts` fixe l'ordre `quality + database → deploy → e2e`, le SHA exact et la clé SSH bornée. `tests/supabase-preflight.test.ts` interdit actuellement toute commande distante dans le préflight local ; AQ-060 doit ajouter un chemin de promotion distinct, testé sans réseau.
- `docs/operations.md` indique encore que les migrations sont manuelles et appliquées avant le code. Il devra documenter l'approbation, les nouveaux secrets, l'artefact chiffré et la reprise manuelle.

## État GitHub vérifié le 11 août 2026

- Le dépôt est public et la branche par défaut est `main`.
- L'environnement `Production` existe et contient uniquement `VPS_HOST`, `VPS_KNOWN_HOSTS`, `VPS_PROJECT_DIR`, `VPS_SSH_PRIVATE_KEY` et `VPS_USER`.
- `Production` n'a actuellement aucune règle de protection. La promesse d'approbation humaine ne sera donc réelle qu'après ajout d'Antoine comme required reviewer et restriction à `main` dans les paramètres GitHub.

## Capacités officielles vérifiées

- Supabase suit les versions appliquées dans `supabase_migrations.schema_migrations`; `supabase migration list` compare l'historique local et distant. `supabase db push --dry-run` énumère les migrations avant mutation, puis `db push` applique uniquement les versions absentes : [Database migrations](https://supabase.com/docs/guides/deployment/database-migrations) et [CLI `db push`](https://supabase.com/docs/reference/cli/supabase-orgs-list).
- La CLI épinglée `2.113.0` installée dans le dépôt expose `migration list --linked`, `db push --linked --dry-run` et `db dump --linked`. Son implémentation `migration list` rend encore un tableau même lorsque le format global JSON est demandé; AQ-060 doit donc parser strictement les deux premières colonnes du tableau et refuser toute sortie inconnue. La promotion utilise cette version exacte avec un `HOME` temporaire.
- Les environnements GitHub peuvent exiger un reviewer et ne livrent leurs secrets au job qu'après approbation. Le dépôt public peut utiliser cette protection : [Deployments and environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments) et [Reviewing deployments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/review-deployments).

## Architecture proposée

1. Ajouter un script borné `scripts/ops/promote-supabase-migrations.sh` exécuté uniquement par le job `deploy` après l'approbation de l'environnement `Production`. Il vérifie les trois secrets Supabase, isole la CLI, lie le project ref attendu, parse strictement l'historique tabulaire et exécute un dry-run.
2. S'il n'existe aucune migration en attente, le script confirme l'alignement sans dump ni mutation. S'il en existe, il produit avant le push des dumps `public` (schéma et données), les archive, les chiffre avec un destinataire `age`, écrit une somme SHA-256, puis applique les migrations avec `db push --linked --yes`.
3. Après le push, une seconde liste/dry-run doit confirmer qu'aucune migration locale ne reste en attente. Les fichiers clairs, le profil Supabase et le mot de passe sont supprimés par `trap`, même en échec. Seuls l'archive `.age`, sa somme et un manifeste sans secret deviennent un artefact GitHub à rétention bornée.
4. Le job `deploy` conserve ensuite le déploiement SSH AQ-058 et la vérification version/santé. Il dépend toujours de `quality` et `database`; les E2E restent après le déploiement.
5. Configurer hors code `Production` avec Antoine comme reviewer requis, branche `main` seulement, et quatre nouvelles valeurs : `SUPABASE_ACCESS_TOKEN`, `SUPABASE_PROJECT_REF`, `SUPABASE_DB_PASSWORD` et `SUPABASE_BACKUP_AGE_RECIPIENT`. Le destinataire age est public par nature mais reste groupé dans l'environnement pour éviter une configuration divergente.

## Sécurité et rollback

- Les secrets distants ne sont jamais disponibles sur une pull request, dans le job local `database`, dans un artefact ou dans le VPS. Le script n'active ni `--debug`, ni `migration repair`, ni `db reset`, ni `--include-all`.
- L'archive de pré-migration est chiffrée avant upload. La clé privée `age` reste hors de GitHub et du VPS; seul le destinataire public est injecté.
- Une migration SQL peut avoir été validée indépendamment avant qu'une migration suivante échoue. AQ-060 ne lance donc jamais de rollback SQL automatique. Il bloque le conteneur candidat, conserve l'application précédente, publie l'artefact de reprise et exige une intervention contrôlée.
- Le rollback applicatif existant reste valide uniquement si les migrations sont rétrocompatibles avec la version précédente. Toute suppression/renommage de colonne ou changement irréversible doit être livré en plusieurs phases et bloquer la promotion tant que l'ancienne application en dépend.
- La mutation distante ne doit être testée que sur le vrai push `main` après approbation. Les tests de PR substituent une fausse CLI et des fixtures, sans secret ni réseau.

## Tests et preuves attendues

- Tests unitaires du parseur de l'historique et du plan de promotion : zéro migration, migrations en attente, divergence locale/distante, échec de dump, échec de push et post-vérification non alignée.
- Tests shell avec faux binaires `supabase`, `age` et `sha256sum` : ordre strict `list/dry-run → dump → chiffrement → push → vérification`, nettoyage et absence de secret dans stdout/stderr.
- Tests statiques du workflow : `deploy` reste limité au push `main`, dépend de `quality` et `database`, référence `Production`, promeut la base avant SSH et téléverse uniquement les fichiers chiffrés.
- Suite complète : `npm test`, `npm run typecheck`, `npm run build`, `npm run quality:budgets`, `bash -n scripts/ops/*.sh`, `git diff --check` et préflight PostgreSQL local.
- Preuve finale : job en attente d'approbation, archive chiffrée si nécessaire, historique distant aligné, SHA exact sain, puis E2E verts.

## Questions résolues et limites

- Une seule approbation est utilisée : le job `deploy` existant reste l'unique job associé à `Production` et contient la promotion puis le VPS.
- Aucun staging Supabase supplémentaire n'est créé dans AQ-060; la pile éphémère AQ-059 reste le préflight.
- La restauration automatique de la base, les migrations destructives et `migration repair` sont hors périmètre. La procédure de reprise est documentée mais demeure manuelle.
