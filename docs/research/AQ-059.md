# AQ-059 — Recherche : préflight Supabase reproductible

## Résultat attendu

Empêcher qu'une migration SQL invalide ou qu'une régression d'isolation arrive jusqu'au déploiement VPS. Chaque pull request et chaque push `main` doivent reconstruire une base Supabase locale éphémère, rejouer le schéma et toutes les migrations, puis exécuter des assertions de sécurité. Ce ticket ne lie aucun projet distant et n'applique aucune migration en production.

## Preuves du dépôt

- `.github/workflows/ci.yml` ordonne désormais `quality → deploy → e2e`, mais le job `quality` ne lance aucune base PostgreSQL et ne valide que les migrations par quelques lectures statiques Vitest (`tests/client-portal-access-migration.test.ts`, `tests/project-profitability-migration.test.ts`, `tests/roadmap-052-057.test.ts`).
- `supabase/schema.sql` crée le socle `organizations`, `organization_memberships`, `clients`, `projects`, `quotes`, `invoices`, `invoice_payments` et active RLS sur les tables privées. Les fichiers de `supabase/migrations/` commencent ensuite par `20260707112422_admin_saved_views.sql`, qui référence déjà `public.organizations` et `auth.users`.
- Il n'existe pas de `supabase/config.toml`, de dépendance CLI Supabase dans `package.json`, ni de tests pgTAP. Le dépôt ne peut donc pas exécuter le workflow officiel `supabase start` / `supabase db reset` de manière versionnée.
- Les migrations récentes contiennent des garanties qu'un vrai PostgreSQL doit valider : clés étrangères composites par organisation (`20260809175124_project_profitability.sql`, `20260810221033_add_recurring_invoices.sql`), fonction atomique `security invoker` avec droits retirés (`20260810221013_add_bank_import_fingerprint.sql`) et tables serveur uniquement avec RLS (`20260810221033_add_recurring_invoices.sql`).
- AQ-058 documente explicitement que les migrations restent manuelles tant qu'il n'existe pas de préflight/préproduction de base (`docs/research/AQ-058.md`, `docs/operations.md`). Le job `deploy` ne doit jamais appeler `supabase db push`.

## Conventions et documentation vérifiées

- Le projet utilise Node `22.19.0`, npm avec lockfile, Vitest et GitHub Actions Ubuntu (`package.json`, `.github/workflows/ci.yml`). La CLI doit donc être une devDependency épinglée et invoquée par `npx supabase`.
- La CLI stable observée le 11 août 2026 est `2.113.0`; `npx supabase db reset --help` confirme `--local` et `--no-seed`, et `npx supabase test db --help` confirme l'exécution pgTAP locale.
- La documentation officielle recommande `supabase db reset` pour prouver que toutes les migrations reconstruisent une base propre et `supabase test db` pour pgTAP. Elle rappelle que `--linked`/`db push` visent un projet distant et qu'un reset distant est destructeur : ces formes seront explicitement interdites dans le script AQ-059.
- Sources consultées : [Supabase CLI](https://supabase.com/docs/guides/local-development/cli/getting-started), [workflow local](https://supabase.com/docs/guides/local-development/cli-workflows), [tests et lint](https://supabase.com/docs/guides/local-development/cli/testing-and-linting), [migrations](https://supabase.com/docs/guides/deployment/database-migrations).

## Architecture proposée

1. Ajouter une configuration locale Supabase sans secret et épingler la CLI.
2. Ajouter un script `scripts/ops/test-supabase-migrations.sh` qui crée un projet temporaire avec `mktemp -d`, place `supabase/schema.sql` comme migration de socle antérieure aux migrations existantes, copie les migrations et tests, lance la pile locale, effectue un reset complet, exécute pgTAP puis arrête et supprime toujours la pile temporaire.
3. Ajouter des tests pgTAP portant sur RLS, les droits `anon`/`authenticated`, la fonction atomique et les contraintes composites critiques. Les tests utilisent uniquement les rôles et données locales.
4. Ajouter un job `database` sans secrets à `.github/workflows/ci.yml`; `deploy` dépend de `quality` et `database`. Une PR exécute le préflight mais ne déploie toujours pas.

Le socle est injecté uniquement dans le projet temporaire. Il ne devient pas une nouvelle migration distante, ce qui évite de falsifier ou désynchroniser l'historique `supabase_migrations` de production.

## Sécurité et limites

- Aucun `SUPABASE_ACCESS_TOKEN`, mot de passe de base, project ref ou URL de production n'est nécessaire.
- Le script doit employer seulement `--local`; les chaînes `--linked`, `db push`, `migration repair` et `db reset --db-url` sont interdites et couvertes statiquement.
- La pile locale ne doit pas être exposée hors du runner. Le nettoyage doit s'exécuter avec un `trap`, y compris après un test en échec.
- AQ-059 ne modifie ni le schéma métier, ni les données, ni les politiques de production. Si pgTAP révèle une faiblesse existante, une correction de schéma doit faire l'objet d'une migration append-only séparée et explicitement revue.
- La pile locale Supabase n'est pas une préproduction hébergée complète; elle couvre la reproductibilité PostgreSQL/Auth et les invariants de droits, pas les paramètres du Dashboard ou les fournisseurs externes.

## Tests et preuves attendues

- Relecture statique du workflow : `deploy.needs` contient `quality` et `database`; aucune PR ne déploie.
- Test du script : syntaxe Bash, projet temporaire, `trap`, commandes locales seulement et version CLI épinglée.
- Exécution réelle locale/CI : démarrage, reset complet depuis le socle, second replay idempotent, pgTAP vert et arrêt propre.
- Suite existante : `npm test`, `npm run typecheck`, `npm run build`, budgets et `git diff --check`.
- Acceptation finale : PR verte sans déploiement; après fusion, `database` et `quality` verts avant le déploiement AQ-058, puis SHA/santé/E2E verts.

## Risques résiduels

- Le premier lancement télécharge plusieurs images Docker et peut allonger la CI; un timeout dédié et des services Supabase minimaux sont nécessaires.
- `schema.sql` est actuellement le socle canonique, mais les changements futurs doivent continuer à être ajoutés par migrations. Le test temporaire ne doit pas transformer le projet en double source de vérité.
- Une vérification de drift avec la production nécessiterait des secrets et un accès distant en lecture; elle reste hors périmètre d'AQ-059.
